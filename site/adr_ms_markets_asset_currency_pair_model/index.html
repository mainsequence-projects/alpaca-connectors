    ADR: ms-markets Currency Pair Asset Model¶

    Status¶

    Proposed

    Context¶

    This repository is starting a migration from the legacy Main Sequence asset usage toward the newer ms-markets asset model.

    The current ms-markets asset design is intentionally narrow:

    • AssetTable stores canonical asset identity
    • AssetTypeTable stores the asset-type registry
    • instrument-specific fields should live in relational detail tables keyed to the asset row

    That design is documented in the current ms-markets asset docs and matches the current source:

    • AssetTable keeps uid, unique_identifier, and asset_type
    • AssetTypeTable registers discoverable type strings such as crypto or equity
    • extension data should be modeled through one-to-one detail tables rather than by widening AssetTable

    The migration needs a first-class way to represent currency pairs such as BTC/USDT.

    That representation must satisfy these requirements:

    • the tradable pair itself must have a canonical asset identity
    • the pair must reference the canonical asset rows for its base and quote legs
    • the leg references must point back to the main asset list, not to free-form strings
    • the design must fit the ms-markets extension pattern instead of adding pair-specific columns to AssetTable

    Decision¶

    Currency-pair assets will be modeled as canonical Asset rows plus a one-to-one relational detail table.

    The first migration decision is:

    1. Register an asset type with key currency and display name Currency.
    2. Represent a tradable pair such as BTC/USDT as an Asset row whose canonical unique_identifier is the ordered pair string.
    3. Add a CurrencyPairDetailsTable keyed by that pair asset.
    4. Store base_asset_uid and quote_asset_uid on the detail table as foreign keys to AssetTable.uid.
    5. Treat the pair asset row as the canonical identity of the tradable pair, while the referenced base and quote assets remain the canonical identity rows for the underlying legs.

    Example:

    • asset BTC
    • asset USDT
    • asset BTC/USDT
    • BTC/USDT has asset_type="currency"
    • CurrencyPairDetailsTable(asset_uid=<BTC/USDT>, base_asset_uid=<BTC>, quote_asset_uid=<USDT>)

    Relational Shape¶

    The intended schema shape is:

    +-----------------------------+        one-to-one pair detail     +-------------------------------+
| AssetTable                  |---------------------------------->| CurrencyPairDetailsTable      |
|-----------------------------|        asset_uid PK/FK            |-------------------------------|
| uid                  PK     |                                   | asset_uid              PK/FK  |
| unique_identifier    unique |                                   | base_asset_uid           FK   |
| asset_type                 |                                   | quote_asset_uid          FK   |
+-----------------------------+                                   +-------------------------------+
          ^                                                                  |
          |                                                                  |
          +--------------------------- foreign keys --------------------------+
                         to canonical leg assets in AssetTable

    Expected identifiers:

    • leg asset BTC
    • leg asset USDT
    • pair asset BTC/USDT

    Expected foreign-key meaning:

    • asset_uid: the pair asset row
    • base_asset_uid: the base leg asset row
    • quote_asset_uid: the quote leg asset row

    Invariants¶

    The migration should preserve these invariants:

    1. AssetTable remains small. Pair semantics do not add base_asset or quote_asset columns directly to AssetTable.
    2. Currency-pair identity is explicit. The tradable pair has its own canonical Asset row.
    3. Pair legs are relational, not textual. Base and quote legs reference canonical asset rows through foreign keys.
    4. Pair direction matters. BTC/USDT and USDT/BTC are different ordered pairs and must not collapse into one record.
    5. Duplicate pair definitions are not allowed. The detail table should enforce uniqueness for the ordered (base_asset_uid, quote_asset_uid) combination.
    6. A pair cannot reference the same asset on both sides. The implementation should reject base_asset_uid == quote_asset_uid.

    Asset Type Rule¶

    This ADR introduces currency as the registered asset-type key for the first currency-pair slice.

    Use:

    • asset_type = "currency"
    • AssetType.display_name = "Currency"

    Important current ms-markets detail:

    • in the current release, Asset.asset_type is a string classification field
    • it is logically aligned to AssetType
    • it is not a database foreign key yet

    This ADR does not require the leg assets themselves to settle all future type questions today. What is decided now is the pair contract:

    • the pair row is classified as currency
    • the pair row owns the canonical tradable-pair identity
    • the pair row references two canonical leg assets

    Whether a leg asset such as BTC or USDT is also classified as currency, crypto, or some other future subtype can be decided in a later ADR if needed.

    Consequences¶

    Positive:

    • The design matches the documented ms-markets extension model.
    • Pair identity is explicit and queryable as a normal asset.
    • Base and quote legs remain normalized against the canonical asset registry.
    • The same leg assets can be reused across many pairs.
    • Future pair-specific metadata can be added to the detail table without widening AssetTable.

    Tradeoffs:

    • Creating one tradable pair now requires at least three coordinated asset records: base asset, quote asset, and pair asset.
    • Pair lookup logic must decide whether callers are asking for a leg asset or a pair asset.
    • A later API/repository layer will need explicit helpers for pair creation and validation; generic Asset.upsert(...) alone is not sufficient to enforce pair invariants.

    Migration Boundary¶

    This ADR decides only the relational asset-model shape for currency pairs.

    It does not yet decide:

    • the exact repository helper names
    • the exact msm.api row model names
    • provider-specific symbol normalization rules
    • price routing or translation-table behavior
    • venue-specific details for FX, crypto, or derivatives exchanges
    • whether existing Alpaca-specific asset registration flows should be retained, wrapped, or replaced

    Those decisions should follow after this schema direction is accepted.

    Follow-On Implementation Shape¶

    When this ADR is implemented, the expected ms-markets layering should be:

    • msm.models.assets.currency_pairs defines CurrencyPairDetailsTable
    • msm.api.assets exposes a typed row model such as CurrencyPairDetails
    • msm.repositories owns compiled create/update/search operations
    • project code under src/ uses those ms-markets assets instead of introducing a parallel local asset schema

    Notes¶

    BTC/USDT is the motivating example for this ADR, but the same pattern is intended for any quoted currency pair whose identity is defined by ordered base and quote assets.
